1 Project Structures

How should I organise a project so that I, and others, can find things and re-run them?

1.1 Why bother?

A project that has grown organically tends to look like a folder full of files called data.csv, data_final.csv, analysis2.R and analysis_NEW.py. This causes three problems:

  • Hard to maintain: one change near the start breaks everything downstream.
  • Hard to run somewhere else: a new laptop, an HPC cluster or a colleague’s machine, and the code breaks.
  • Hard to understand: after a holiday you can’t remember which file to run first.

Making a project more reproducible helps you first and others second:

  • Saving your future self: write code as if someone else will use it, because in six months that someone is you.
  • Speed: a project set up as a pipeline can be re-run quickly when the data or a reviewer’s comment changes.
  • Confidence: you understand how the work fits together, and where it might fail.
  • Publication and jobs: sharing code and data is an increasingly common requirement, and tidy work is easy to trust.
TipYou don’t need everything

How much structure a project needs is a judgement call. A small one-off analysis may not need all of this. Aim for what is useful, not what is perfect.

1.2 A messy project

Open messy-project/ in the example folder. It looks like this:

messy-project/
├── Copy of data.csv
├── analysis.R
├── analysis2 (copy).R
├── analysis_OLD.R
├── clean.R
├── data.csv
├── data_FINAL_USE_THIS.csv
├── data_final.csv
├── data_final_v2.csv
├── notes.txt
├── plot1.png
├── plot_new.png
├── report_draft.docx
├── results.xlsx
├── results_v3.xlsx
└── untitled.R

Questions to ask of this layout:

  • Which file is the raw data?
  • What do I run first?
  • Which figure came from which analysis?

This happens naturally. You start by exploring a dataset in a notebook, a script or an Excel sheet. The analysis grows, then a second analysis is added, and it becomes hard to see how you got from the raw data to the results.

1.3 A tidy project

Now open tidy-project/. It holds the same project, organised:

tidy-project/
├── README.md
├── report.qmd
├── _quarto.yml
├── data/
│   ├── raw/penguins.csv
│   └── processed/
│       ├── penguins_clean.csv
│       └── penguins_clean_dictionary.csv
├── code/
│   ├── 01_clean_data.R
│   └── run_all.R
└── outputs/

The key ideas are:

  1. A README at the top of the project says what it is and how to use it (see the next section).
  2. Raw data is read-only. Never overwrite your original data file. Save the cleaned version somewhere else.
  3. Code is a pipeline. Each step reads the output of the previous step: raw data -> clean -> analyse -> results. Numbering the files shows the order to run them in.
  4. Results can be thrown away. Anything in outputs/ and data/processed/ can be re-made by running the code. code/run_all.R does exactly that: delete them, run it, and they come back.

Spreadsheets. The same structure works for spreadsheets:

  • Keep the original file in a data/raw folder and never edit it. Open it, then use Save As to put a working copy in data/processed.
  • Use one sheet per step, in order, and name them (1_raw, 2_cleaned, 3_results) rather than leaving Sheet1.
  • Write down in the README what you did to the data at each step, in enough detail that someone else could repeat it.
  • Put formulas in cells rather than pasting values, so the calculation is visible.
TipYou don’t need everything

How much structure a project needs is a judgement call. A small one-off analysis may not need all of this. Aim for what is useful, not what is perfect.

TipKey points
  • Separate raw data, cleaned data, code and results.
  • Never overwrite the raw data.
  • Think of the analysis as a pipeline that can be re-run from start to finish.
  • This applies equally to scripts, notebooks and spreadsheets.

2 Documentation & Quarto

How do I explain my project, and report on it, so others (and future me) can use it?

2.1 Types of documentation

Type Where Why Audience
Comments in code Scripts, notebooks, function docstrings Explain or justify what isn’t obvious from the code Other researchers and developers
Files in the repository README.md Describe how to use the project Developers, and people running the code
Data dictionary A CSV next to the data Explain what each column means, its units and missing values Anyone using the data
External documentation A website or report Describe what you are doing in less technical terms, with quickstart guides Users and less technical readers

A good comment says why, not what. # remove outliers > 3 SD, as agreed with the lab is more useful than # remove outliers.

2.2 README.md

A README is a plain text file in the top folder of the project. It is the first thing someone reads, and it helps you in six months’ time as much as it helps anyone else. It should contain:

  • Summary: what the project is for, and its status (for example ongoing or complete).
  • Quickstart: the most important files, and in what order to run them.
  • Setup: what needs to be installed before running the code.
  • Contents: a description of what each folder holds.

Here is the README from tidy-project/. It is written in Markdown, which is a simple way of marking up text:

# Penguin body mass analysis

Body measurements of 333 penguins on three islands. **Status:** complete.

## Quickstart

1. Open this folder in RStudio or Positron (or a terminal).
2. Run `code/run_all.R`. It cleans the data and builds the report in `outputs/`.

## Setup

- R 4.3 or later (no extra packages needed)
- Quarto 1.4 or later (to make the report)

## Contents

- `data/raw/` the original data (never edited)
- `data/processed/` the cleaned data, and a data dictionary explaining each column
- `code/` the scripts
- `report.qmd` the report, which makes HTML, PDF and Word versions
- `_quarto.yml` settings for the report (it puts the results in `outputs/`)
- `outputs/` made by `run_all.R`. Safe to delete

You can use a README in any project, whether or not you write code. For a spreadsheet project it is the place to record what each sheet does and how the data was collected.

2.3 Data dictionary

A dataset on its own doesn’t explain itself. What does bill_dep mean? Is body_mass in grams or kilograms? Does a blank mean it wasn’t measured? Write this down in a data dictionary, a small table with one row per column:

column type description units / values
species text Penguin species Adelie, Chinstrap, Gentoo
island text Island where the penguin was observed Biscoe, Dream, Torgersen
bill_len number Bill length mm
bill_dep number Bill depth mm
flipper_len number Flipper length mm
body_mass number Body mass grams
sex text Sex of the penguin female, male; blank if not recorded
year number Year of the study 2007, 2008 or 2009

Save it next to the data (for example data/processed/penguins_clean_dictionary.csv) and refer to it from your README. You can also include a short description of the whole dataset: who collected it, when, how, and any known problems. A dictionary is one of the most valuable things you can write, because only the person who knows the data can.

To make one, copy your column names into a spreadsheet or CSV file, then add columns for the type, a description, and the units or values. Fill them in by hand, and save the file as a CSV next to the data.

2.4 What is Quarto?

Quarto is a free, open-source tool for writing documents that combine text and code. You write one file (report.qmd). When you render it, the code runs, and the results (numbers, tables and figures) are put into a finished document, such as an HTML page, a PDF or a Word file.

Quarto works with R, Python and other languages, from the IDE you already use. The slides, the notes and the website for this course are all made with Quarto.

2.5 Why use Quarto for reproducible research?

A report is often the last step of an analysis, and the easiest place to introduce mistakes: a number is copied from the wrong run, or a figure is from an older version of the data. Quarto removes that step.

  • No copy and paste. Numbers, tables and figures come straight from the code, so they can’t drift out of sync with the analysis.
  • Always up to date. If the data changes, render again and the whole report updates.
  • One source, many outputs. The same file can make HTML, PDF, Word, slides and websites.
  • Plain text. A .qmd file is easy to share, compare and keep in version control, in any editor.
Without Quarto With Quarto
1 Run the analysis Write the report once, with the code in it
2 Copy numbers and plots into a Word document Render
3 The data changes The data changes
4 Repeat by hand, and hope you caught every number Render again

2.6 Weaving text and analysis together

A Quarto file has four ingredients:

  1. A header with the title and the output format (between two lines of ---).
  2. Text, written in Markdown: headings, paragraphs, lists and links.
  3. Code chunks: R or Python code in a fenced block. When you render, the code runs and its output (a table, a plot) appears underneath.
  4. Inline code: a result inside a sentence, which is recalculated every time you render.
  • R
  • Python
  • Excel / no code
report.qmd
---
title: "Penguin report"
format: html
---

## Data

```{r}
clean <- read.csv("data/processed/penguins_clean.csv")

# keep one species: filter out Adelie and Chinstrap
gentoo <- subset(clean, species == "Gentoo")
```

After removing incomplete rows, there are `{r} nrow(clean)` penguins in the data. `{r} nrow(gentoo)` of them are Gentoo penguins.

## Results

The mean body mass of Gentoo penguins was `{r} round(mean(gentoo$body_mass))` g.

```{r}
boxplot(body_mass ~ sex, data = gentoo, ylab = "Body mass (g)")
```
report.qmd
---
title: "Penguin report"
format: html
---

## Data

```{python}
import pandas as pd

clean = pd.read_csv("data/processed/penguins_clean.csv")

# keep one species: filter out Adelie and Chinstrap
gentoo = clean[clean["species"] == "Gentoo"]
```

After removing incomplete rows, there are `{python} len(clean)` penguins in the data. `{python} len(gentoo)` of them are Gentoo penguins.

## Results

The mean body mass of Gentoo penguins was `{python} round(gentoo["body_mass"].mean())` g.

```{python}
gentoo.boxplot(column="body_mass", by="sex")
```

(The plot needs the matplotlib package.)

Quarto can be used for the written part of a project even if your analysis is in a spreadsheet. Save your final table as a CSV, then include it in the report:

report.qmd
---
title: "Penguin report"
format: html
---

Results from the spreadsheet analysis:

```{r}
knitr::kable(read.csv("outputs/tables/results.csv"))
```

This still needs R installed. If you’d rather not use code at all, a README and clearly labelled sheets are the best documentation you can write.

2.7 When the data changes

Because the numbers in the report come from code, a change in the data flows through to the report:

new data  ->  re-run the cleaning script  ->  render the report  ->  updated report

Every number, table and figure is recalculated, and sentences with inline code update too. There is nothing to copy and paste. This is the main reason to use Quarto for reproducible research: change the data (or the code), not the report.

2.8 One document, many formats

One of the best things about Quarto is that one source file can make several kinds of document. You list the formats you want in the header:

format:
  html: default
  typst: default
  docx: default
  • html makes a web page.
  • typst makes a PDF. Typst comes with Quarto, so you don’t need to install LaTeX.
  • docx makes a Word document.

When you render, Quarto makes all three from the same text, code and figures. Change the title, a sentence or the data once, and every format changes.

To render, press the Render button in your IDE (use the format menu to choose which one), or run this in a terminal to make every format at once:

Terminal/Command Prompt
quarto render report.qmd

2.9 Rendering

Render the report from the terminal, or with the Render button in your IDE:

Terminal/Command Prompt
quarto render report.qmd

The result, report.html, appears next to report.qmd.

2.10 What else can Quarto do?

  • Reports in HTML, PDF and Word, with tables, figures and references.
  • Slides: the slides for this course are a Quarto presentation.
  • Websites: this course website is built with Quarto.
  • Papers and books: journal articles, theses and books, with citations and cross-references.

3 Virtual Environments

How do I make sure my code still runs next month, or on someone else’s computer?

3.1 Why do we need environments?

Imagine this sequence:

  1. Last year you wrote an analysis, and it runs, using version 1.2.1 of a package (here, the R package tidyr).
  2. This year you start a new project that needs version 1.3.1, so you update.
  3. You re-run last year’s analysis, and it breaks, or gives different results.
Old project New project
Program R 4.3.0 R 4.3.0
tidyr 1.2.1 1.3.1
ggplot2 3.3.5 3.5.0

Your computer has one shared set of packages, so two projects that need different versions can’t both be happy. This happens for several reasons:

  • Packages change. Functions are renamed, defaults change and bugs are fixed.
  • Your code depends on them. The same code with a different package version can give a different result.
  • Other computers differ. A colleague, a new laptop or an HPC cluster will have different versions installed: “it works on my machine”.
  • Nothing records it. Your project doesn’t say which versions it needs, so nobody can tell what went wrong.

3.2 What is an environment, and how does it work?

An environment is a project’s own set of packages, at the versions it needs. Instead of one shared library for every project, each project has its own, so projects can’t interfere with each other.

Environments work with two things:

  • A lock file is the recipe: an exact list of packages and versions. It is a small text file, and you keep it with your project.
  • The environment is what gets built from the lock file: the installed packages, in their own folder. Your code only sees the packages in its own environment.

The environment is disposable: you can delete it, and rebuild it from the lock file whenever you like. The lock file is the thing you keep.

Tool uv renv conda pixi
Works with Python R Python, R and other software Python, R and other software
Lock file (keep it) uv.lock renv.lock environment.yml* pixi.lock
Environment (disposable) .venv renv/library Kept by conda, outside your project .pixi
Rebuild it uv sync renv::restore() conda env create -f environment.yml pixi install

uv and renv each work with one language. conda and pixi can install Python, R, and other software that isn’t a package for either (such as GDAL or a C library), which helps if a project mixes languages. pixi is the newer of the two, and works like uv: it keeps the environment in the project folder and writes a lock file for you.

* environment.yml lists the packages, but not always their exact versions, so it isn’t a true lock file. Make it with conda env export > environment.yml, or use conda-lock for a full lock file.

Other tools do the same job, such as Python’s built-in venv with a requirements.txt file. The idea is the same whichever you use: a file that records what the project needs.

3.3 Send your project to someone, and it works

This is the payoff. Because the lock file records exactly what the project needs, you can send your project to a colleague, a reviewer, or yourself on a new laptop, and they can rebuild the same environment with one command:

your project + lock file  ->  colleague rebuilds the environment  ->  same packages, same results
  • Send: your code, README and lock file (and the data, if you can share it).
  • Don’t send: the environment itself. It is large, and specific to your computer.

3.4 What environments don’t cover

  • They record packages. Also write down the version of R or Python in your README. (uv can pin the Python version; renv records the R version but doesn’t install it.)
  • The operating system and hardware can still differ.
  • They don’t include your data.

That is good enough for almost every project. Perfect is not the goal.

3.5 What if I use Excel?

There are no packages to install, but the software version can still matter: formulas and functions differ between Excel versions, and add-ins vary. Write the program and its version in your README (for example Excel for Microsoft 365, version 2410), along with any add-ins used. The next person then knows what you used, which is the same idea.

You do not need to run any commands in this course. If you want to try environments yourself:

  • To give a project of your own an environment, in R (with renv) or Python (with uv), work through the final exercise at the end of these notes.

4.1 From messy to shareable

This whole course is one journey:

Messy  ->  Tidy  ->  Documented  ->  Reported  ->  Recorded  ->  Shareable

5 Optional: Sharing Your Data (Q-FAIR)

How do I know my data is good enough to share, and how do I share it?

This section is optional in the live course, but it is written in full so you can work through it on your own.

5.1 Q-FAIR data principles

The FAIR principles are a well-known checklist for sharing data. Q-FAIR adds Quality at the start:

Letter Principle What it means in practice Where we met it
Q Data Quality Data is accurate, complete and documented. You know where it came from and what was done to it. Raw data is never overwritten; the pipeline records every change.
F Findable People, and computers, can find it. It has a clear name and description. Clear folder layout and a README.
A Accessible It is clear how to get the data, and under what conditions. README setup and access notes.
I Interoperable It uses open, standard formats that other tools can read. CSV, not a locked format.
R Reusable Others can understand and re-use it, with a clear licence. A README and a data dictionary.

5.2 Why it matters

  • Funders and journals increasingly expect data to be shared.
  • Others can build on your work, and check it.
  • Future you can find and understand your own data.
  • Your work gets cited.

5.3 A worked example

Here is how the two example projects score against each letter:

Question tidy-project/ messy-project/
Q Can you trust it, and do you know what was done to it? ✔ The raw data is untouched and the code records every change ✘ Three cleaned versions, and some values were fixed by hand
F Can people find it? ✔ Clear names and a README ✘ data_FINAL_USE_THIS.csv
A Is it clear how to get it? ✔ The README says where everything is ✘ “Ask Sam”
I Is it in an open format? ✔ CSV ✘ Results in .xlsx
R Can others understand and reuse it? ✔ A data dictionary (it still needs a licence) ✘ Columns not explained, no licence

5.4 Four things to do

1. Use open file formats. Share data as CSV (comma-separated values), which is plain text that every tool can read, rather than a format that needs one program. In Excel, use File > Save As and choose CSV UTF-8. A CSV holds one sheet only, and keeps values, not formulas.

2. Describe your data. Write a data dictionary, with one row per column, as in the Documentation section, and keep it next to the data.

3. Add a licence. Without one, others don’t know whether they can reuse your work. Common choices are CC BY 4.0 for data and text, and MIT for code. The Creative Commons chooser and choosealicense.com can help. Your funder or institution may have requirements, so check first.

4. Deposit it. Put the data in a repository that gives it a permanent home and a DOI (a persistent identifier you can cite), such as Zenodo, your institution’s data repository (at Bristol this is data.bris), or one specific to your field.

Sensitive data. Some data can’t be shared openly, for example because it contains personal information. You can usually still share the metadata (the README and data dictionary) and explain how others can apply for access. Check with your research data team or ethics committee before depositing anything involving people.

TipKey points
  • Q-FAIR: data Quality, Findable, Accessible, Interoperable, Reusable.
  • Share data in open formats such as CSV, with a data dictionary and a licence.
  • Deposit it in a repository that gives it a DOI.
  • If data can’t be shared, share the metadata and explain how to ask for access.

6 Optional: Putting It All Together

Can I build a project, from scratch, that someone else could run?

This is an exercise to do after the course, on your own. It uses every section: you build a tidy project, give it an environment, and write a report with code in it, laid out like a short paper. At the end, you test it the way a colleague would.

It takes about an hour or two. Do it in R or in Python: where the steps differ, there is a tab for each. You need:

  • Quarto, version 1.4 or later (see Workspace setup).
  • R or Python, and the tool for its environment. For R, that’s the renv package (install it with install.packages("renv")). For Python, install uv. uv can install Python for you, so you don’t need Python already.
  • The example folder, for the raw data.

6.1 What you will build

penguin-project/
├── README.md                     what it is, and how to run it
├── _quarto.yml                   puts the report in outputs/
├── report.qmd                    the report
├── references.bib                the reference list
├── data/
│   ├── raw/penguins.csv          the original data (never edited)
│   └── processed/                made by the cleaning script
├── code/01_clean_data.R (or .py) cleans the data
├── outputs/                      the rendered report (HTML, PDF, Word)
└── the environment               renv.lock or uv.lock: the lock file

6.2 Step 1: A tidy project

Make a new folder called penguin-project, somewhere outside the example folder. Inside it, make the folders data/raw, data/processed, code and outputs.

Copy tidy-project/data/raw/penguins.csv from the example folder into data/raw/. This is your raw data: from now on, you never edit it.

Start a README.md. You’ll finish it in step 5, but write down what the project is now:

README.md
# Penguin body mass

Does body mass differ between male and female Gentoo penguins?
**Status:** in progress.

## Data

Penguin measurements from near Palmer Station, Antarctica
(Gorman, Williams and Fraser, 2014).

6.3 Step 2: An environment

Open a terminal (or, for R, RStudio or Positron) in the penguin-project folder, and give the project its own environment.

  • R
  • Python

In RStudio, make the folder a project first: File → New Project → Existing Directory. In Positron, open the folder. Then run these in the R console:

renv::init()                                 # give this project its own environment
install.packages(c("knitr", "rmarkdown"))    # Quarto needs these to run R code

renv::init() makes the lock file, renv.lock, and a renv/ folder, which holds the environment. From now on, the packages you install in this project go into its own environment, and don’t affect your other projects. You’ll record them in the lock file in step 5.

Terminal/Command Prompt
uv init --no-package
uv add pandas matplotlib jupyter tabulate

uv init makes pyproject.toml and .python-version, and a starter main.py, which you can delete. uv add makes the environment (the .venv folder), installs the packages into it, and records them in the lock file, uv.lock. pandas and matplotlib are for the analysis. Quarto needs jupyter to run Python code, and tabulate helps it make tables.

--no-package keeps the project simple: without it, newer versions of uv set the project up as a Python package to share, which this project doesn’t need.

6.4 Step 3: Clean the data

Write a script that reads the raw data, removes the incomplete rows, and saves a clean copy in data/processed/. The raw file is never changed.

  • R
  • Python
code/01_clean_data.R
# Reads the raw data, removes incomplete rows, and saves a clean copy.
# Run from the project folder: Rscript code/01_clean_data.R

raw <- read.csv("data/raw/penguins.csv")
clean <- na.omit(raw)
write.csv(clean, "data/processed/penguins_clean.csv", row.names = FALSE)

Run it:

Terminal/Command Prompt
Rscript code/01_clean_data.R

Or open the script in RStudio or Positron, and press Source.

code/01_clean_data.py
"""Reads the raw data, removes incomplete rows, and saves a clean copy.

Run from the project folder: uv run code/01_clean_data.py
"""
import pandas as pd

raw = pd.read_csv("data/raw/penguins.csv")
clean = raw.dropna()
clean.to_csv("data/processed/penguins_clean.csv", index=False)

Run it inside the environment:

Terminal/Command Prompt
uv run code/01_clean_data.py

Then write a data dictionary for the clean data, data/processed/penguins_clean_dictionary.csv, with one row per column: its name, type, description and units. Look at the first rows of the data to work them out. If you get stuck, compare yours with the one in tidy-project/data/processed/.

6.5 Step 4: Write the report

Make a file called _quarto.yml in the project folder, so that everything Quarto makes goes in outputs/:

_quarto.yml
project:
  output-dir: outputs

Then make report.qmd, and build it up one part at a time. Render after each part to see what changed:

  • R
  • Python

Press Render in RStudio or Positron, or run this in a terminal. Quarto uses the project’s environment by itself.

Terminal/Command Prompt
quarto render report.qmd

Render it with uv run, so that Quarto uses the project’s environment:

Terminal/Command Prompt
uv run quarto render report.qmd

4a. A header like a paper’s. As well as the title, add a date, an abstract, numbered sections and a table of contents. echo: false hides the code, so readers see only the results. The code is still in the file.

report.qmd
---
title: "Body mass of Gentoo penguins"
author: "Your name here"
date: today
abstract: |
  Male Gentoo penguins are heavier than females. This report
  measures the difference.
number-sections: true
execute:
  echo: false
format:
  html:
    toc: true
    embed-resources: true
  typst: default
  docx: default
---

4b. Read the data. Under the header, add a chunk that reads the clean data and keeps one species, and a sentence with inline code, so the number updates when the data changes:

  • R
  • Python
report.qmd
```{r}
clean <- read.csv("data/processed/penguins_clean.csv")
gentoo <- subset(clean, species == "Gentoo")
by_sex <- aggregate(body_mass ~ sex, data = gentoo, FUN = mean)
```

## Data

After removing incomplete rows, there are `{r} nrow(gentoo)` Gentoo
penguins in the data.
report.qmd
```{python}
import matplotlib.pyplot as plt
import pandas as pd
from IPython.display import Markdown

clean = pd.read_csv("data/processed/penguins_clean.csv")
gentoo = clean[clean["species"] == "Gentoo"]
by_sex = gentoo.groupby("sex")["body_mass"].mean().round()
```

## Data

After removing incomplete rows, there are `{python} len(gentoo)` Gentoo
penguins in the data.

4c. A table, with a caption. Add a ## Results heading, then a chunk whose label starts with tbl-. Quarto numbers it as a table:

  • R
  • Python
report.qmd
```{r}
#| label: tbl-sex
#| tbl-cap: "Mean body mass of Gentoo penguins, by sex"
knitr::kable(by_sex, col.names = c("Sex", "Mean body mass (g)"), digits = 0)
```
report.qmd
```{python}
#| label: tbl-sex
#| tbl-cap: "Mean body mass of Gentoo penguins, by sex"
table = by_sex.reset_index()
table.columns = ["Sex", "Mean body mass (g)"]
Markdown(table.to_markdown(index=False))
```

4d. A figure, with a caption. In the same way, a label starting with fig- makes a numbered figure. fig-alt describes it for people who use a screen reader:

  • R
  • Python
report.qmd
```{r}
#| label: fig-mass
#| fig-cap: "Body mass of Gentoo penguins, by sex"
#| fig-alt: "Boxplot of Gentoo body mass: males are heavier than females"
boxplot(body_mass ~ sex, data = gentoo, xlab = "Sex", ylab = "Body mass (g)")
```
report.qmd
```{python}
#| label: fig-mass
#| fig-cap: "Body mass of Gentoo penguins, by sex"
#| fig-alt: "Boxplot of Gentoo body mass: males are heavier than females"
ax = gentoo.boxplot(column="body_mass", by="sex", grid=False)
ax.set_title("")
plt.suptitle("")
ax.set_xlabel("Sex")
ax.set_ylabel("Body mass (g)")
plt.show()
```

4e. Refer to them. Write @tbl-sex or @fig-mass in the text, and Quarto replaces it with “Table 1” or “Figure 1”, with a link. The numbers stay right if you add more tables or figures. Put the result in a sentence too, with inline code:

  • R
  • Python
report.qmd
On average, males were `{r} round(diff(by_sex$body_mass))` g heavier
than females (@tbl-sex and @fig-mass).
report.qmd
On average, males were `{python} int(by_sex["male"] - by_sex["female"])` g heavier
than females (@tbl-sex and @fig-mass).

4f. Cite a source. Make a file called references.bib, with the paper the data comes from. (Reference managers such as Zotero can export .bib files for you.)

references.bib
@article{gorman2014,
  title   = {Ecological Sexual Dimorphism and Environmental Variability
             within a Community of {Antarctic} Penguins (Genus {Pygoscelis})},
  author  = {Gorman, Kristen B. and Williams, Tony D. and Fraser, William R.},
  journal = {PLoS ONE},
  year    = {2014},
  volume  = {9},
  number  = {3},
  pages   = {e90081},
  doi     = {10.1371/journal.pone.0090081}
}

Add bibliography: references.bib to the header. Add an ## Introduction that cites it with [@gorman2014], and a ## References heading at the end. Quarto adds the citation, and the reference list under that heading.

4g. Render all the formats. Open the HTML, PDF and Word versions in outputs/. The section numbers, captions, cross-references and citation are in all three, from one file. You should find 119 Gentoo penguins, with males about 805 g heavier than females.

6.6 Step 5: Record it

Record the packages in the lock file, and finish the README.

  • R
  • Python
renv::snapshot()

renv looks through the project’s code for the packages it uses, and records them, at the versions installed, in renv.lock.

There is nothing to do: uv add already recorded the packages in uv.lock.

Now finish the README, so that someone else can run the project. Add a Quickstart (what to run, in order), a Setup (the software and versions it needs, including the version of R or Python) and the Contents (what is in each folder). Use tidy-project/README.md as a model. Change the status to complete.

6.7 Step 6: The new laptop test

Now test your project the way a colleague would, on a computer that has never seen it. Delete everything that can be re-made: the environment, data/processed/penguins_clean.csv and the outputs/ folder. Then follow your own README to rebuild it:

  • R
  • Python

Delete the renv/library folder, then restart R. Rebuild the environment from the lock file, then run the project:

renv::restore()
Terminal/Command Prompt
Rscript code/01_clean_data.R
quarto render report.qmd

Delete the .venv folder. (It’s a hidden folder, so you may need to show hidden files to see it.) Then rebuild the environment from the lock file, and run the project:

Terminal/Command Prompt
uv sync
uv run code/01_clean_data.py
uv run quarto render report.qmd

Do you get the same report, with the same numbers? If anything was missing from your README, add it. For a real test, zip the project (without the environment) and send it to a colleague: can they run it from the README alone?

6.8 Going further: a full paper

Quarto can also make a whole journal article, called a manuscript, from one or more .qmd files or notebooks. It publishes the paper as a website, with the PDF, Word and JATS versions, and the code and notebooks behind each figure, side by side. Quarto’s tutorial works through an example paper, La Palma Earthquakes, which is a good model to copy for your own paper. There is a version for each way of working, and each has a template on GitHub that you can copy and render yourself:

  • R: the RStudio tutorial, with its template.
  • Python: the VS Code tutorial, with its template.
  • Jupyter notebooks: the JupyterLab tutorial, with its template.

Other ways to take it further:

  • Add a code/run_all.R (or .py) that rebuilds everything from the raw data in one go, like the one in tidy-project/.
  • Put the project in git, and on GitHub. We cover this in a separate git and GitHub course.
  • Share the data. See the Q-FAIR section above.
