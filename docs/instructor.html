At a glance

How it runs: slides, then short “I do, you do” steps (cycles) on the example folder, then an exercise. The steps for each cycle and demo are in the speaker notes of its slide (press S in the deck).

# Section Min Objective Cycles and exercise
1 Project structures 30 1 Cycles 1-2, Exercise 1
2 Documentation & Quarto 45 2, 3 Cycles 3-6, Exercise 2
3 Virtual environments 30 4 Demo 4, Exercise 3
4 Sharing data: Q-FAIR 15 5 Exercise 4

By the end, attendees can:

  1. Organise a project into raw data, processed data, code and outputs, and explain why raw data is never edited.
  2. Write a README and a data dictionary that help others understand and use their project.
  3. Explain why Quarto helps reproducibility, and build a report that updates when the data changes.
  4. Explain why environments matter, and record the software a project needs so it can be re-run on another computer.
  5. Check a dataset against the Q-FAIR principles, and know where to find out more about sharing data.

Before you start

  • Download and unzip the example folder, and rehearse each cycle once.
  • Check Quarto (1.4 or later; RStudio and Positron include it) and press Render on report.qmd.
  • Render finished/report.qmd once and save report.html next to it, as a fallback for anyone whose Render fails. Then run python3 build_example_zip.py.
  • Ask attendees which they use (R, Python or spreadsheets), and remind them about Quarto and uv / renv.
  • Check the name of the institutional data repository (data.bris) and the links.

Ground rules

  • This is not a coding course. Never debug code live. If something fails, use the ready-made file in finished/ and carry on.
  • You demo in R and Positron. Python and spreadsheet users follow the same steps with their own tools; the notes show Python versions.
  • Say less, show more. If running late, skip a “you do”, not a section.

1 1. Project structures (30 min)

Checkpoints: by 7 min cycle 1; by 14 cycle 2; by 20 Exercise 1; finish at 30.

Key messages

  • Raw data is never edited: everything else can be re-made from it.
  • Raw / processed / code / outputs, and the pipeline idea.
  • Messy projects happen naturally. Nobody is being criticised.
  • Spreadsheets: same rule. Keep the original, work on a copy.

Don’t forget

  • Ask who has a messy project like the one on the slide.
  • Say out loud: “if it doesn’t work, use finished/”.
  • Relative paths, not C:/Users/me/....

If running late: run the cleaning script as a demo only. Watch out for: “it is quicker to fix the typo in the raw file”.

2 2. Documentation & Quarto (45 min)

Checkpoints: by 6 min cycle 3; by 12 cycle 4; by 17 Quarto slides; by 27 cycle 5; by 34 cycle 6; by 39 Exercise 2; finish at 45.

Key messages

  • Four kinds of documentation. Write for the person who will read it.
  • README: summary, quickstart, setup, contents. A README that is wrong is worse than none.
  • Data dictionary: copying the column names is easy. The descriptions are the value.
  • Quarto: the report is the analysis. No copy and paste. Data changes, so render again.
  • This deck, the notes and the course website are all Quarto.

Don’t forget

  • Open the Quarto part with “who has copied a number into Word and then found the data had changed?”
  • Point at each part of a .qmd: header, text, code chunk, inline code.
  • Ask “what would a colleague need to ask me next year?” for the dictionary.
  • Show the “Learn more about Quarto” slide at the end.

If running late: drop cycle 6 and do it as part of Exercise 2. Watch out for: Render failing (Quarto or R not set up). Show it on your screen and use finished/report.html. Inline code needs Quarto 1.4 or later. Spreadsheet users: the README and the idea matter, Quarto is optional.

3 3. Virtual environments (30 min)

Checkpoints: by 10 min the demo; by 18 IDE vs CLI; by 20 Exercise 3; finish at 30.

Key messages

  • “It worked last year”: packages change, and one computer has one shared set.
  • An environment is a project’s own packages. The lock file is the recipe, and the environment is disposable.
  • Send your project to someone: send the code, README and lock file, not the environment. They rebuild it with one command.
  • What it doesn’t cover: the R or Python version, the operating system, the data.
  • Spreadsheets: write the program and its version in the README.

Don’t forget

  • Spend the time on the why. The demo is the easy bit.
  • When you delete and restore: “this is what your colleague does”.
  • renv records package versions, not the version of R. Say so.
  • IDE vs CLI: the file matters, not how you made it. Say “yours will have something similar”.
  • The exercise is for people whose tools are set up. Everyone else does the no-code version.

If running late: demo only R, or only Python. Watch out for: uv not on the PATH (restart the terminal), locked-down laptops (pair people up), and mixing up the environment (delete it) with the lock file (keep it).

4 4. Sharing data: Q-FAIR (15 min)

Checkpoints: by 4 min the four things; by 9 Exercise 4; recap at 14; finish at 15.

Key messages

  • Q-FAIR: Data Quality, Findable, Accessible, Interoperable, Reusable.
  • Why it matters: funders and journals, others can build on and check your work, future you, citations.
  • Four things to do: open formats (CSV), a data dictionary, a licence, deposit it (DOI).
  • Can’t share the data? Share the README and data dictionary, and explain how to ask for access.

Don’t forget

  • Link Q, F and A back to earlier sections.
  • This is a signpost, not a tutorial: no demo, and the links do the work.
  • Don’t give ethics or consent advice. Refer people to the research data team.
  • Finish on the recap slide and tick off the five objectives. Mention the separate git and GitHub course.

Watch out for: Excel saving the wrong CSV type. Use CSV UTF-8, one sheet per file, and remember formulas become values.
