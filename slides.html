01 Project structures

How should I organise a project so I, and others, can find things and re-run them?

Why bother?

Future you Code written as if others will use it is easier to return to after a holiday, or in six months’ time

Speed A project set up as a pipeline can be re-run quickly when the data changes or a reviewer asks for something new

Confidence You understand how the pieces fit together, and where things might go wrong

Sharing and careers Journals and funders increasingly expect shared code and data, and tidy work is easy to trust

Selfish reasons first: this mostly helps you. Mention the three problems with a messy project: hard to maintain, hard to run somewhere else, hard to understand.

Think about pipelines

Raw data → Clean → Analyse → Results

  • Never overwrite the raw data
  • Everything after it can be re-made by running the code
  • So the raw data and the code are what you must protect

Spreadsheet users: same idea. Raw file untouched, a working copy, one named sheet per step, and a README describing each step.

02 Documentation & Quarto

How do I explain my project, and report on it, so others (and future me) can use it?

Four kinds of documentation

Comments in code Files in the repo Data dictionary External documentation
Where Scripts and notebooks README.md A CSV next to the data A website or report
Why Explain why, not what How to use the project What each column means What you did, in plain terms
Who for Other researchers People running your code Anyone using the data Less technical readers
Example # outliers removed, as agreed with the lab Quickstart and setup bill_len: bill length, in mm A Quarto report


Write for the person who will read it, which includes yourself!

Go through the four in turn, and ask who they are writing for. Comments are for people reading the code, the README is for people running it, the data dictionary is for people using the data, and external documentation is for people who may never see the code. The rest of this section covers the README, the data dictionary and reports written in Quarto.

What goes in a README?

  • Summary and status
  • Quickstart: which files, in what order
  • Setup: what to install first
  • Contents: what each folder holds

Using AI

Be careful getting an LLM to create your README. While it can save time, you may inadvertently upload all your data and results by giving access to your folders! Instead, draft one yourself and then use a chatbot to help refine it!

What is Quarto?

  • Write text and code in one file
  • Render it into a report: HTML, PDF or Word
  • The results come from the code
  • Free and open source: quarto.org

report.qmd → HTML PDF Word

Quarto is the tool this whole course is built with: the slides, the notes and the website are all Quarto. It is free, and works with R, Python and Julia.

Why Quarto for reproducible research?

No copy and paste Numbers, tables and figures come straight from the code, so they can’t drift out of sync with the analysis

Always up to date If the data changes, render again and the whole report updates

One source, many outputs The same file can make HTML, PDF, Word, slides and websites

Plain text Easy to share, compare and keep in version control, in any editor

The key idea is that the report is the analysis. A reader, or you in six months, can see exactly how every number was produced, and re-create it.

The old way vs the Quarto way

Without Quarto

  1. Run the analysis
  2. Copy numbers and plots into a Word document
  3. The data changes
  4. Repeat by hand, and hope you caught every number

With Quarto

  1. Write the report once, with the code in it
  2. Render
  3. The data changes
  4. Render again

Ordinary Markdown, with headings and lists

  • Sentences with inline code update too

03 Virtual environments

How do I make sure my code still runs next month, or on someone else’s computer?

The problem: “it worked last year”

  1. Last year: your analysis runs, using version 1.2 of a package
  2. This year: a new project needs version 1.3, so you update
  3. You re-run last year’s analysis: it breaks, or gives different results 💥

Your computer has one shared set of packages, so two projects that need different versions can’t both be happy

Everyone who has coded for a while has had this. The same code, a different version of a package, and a different result, or an error. Ask who has had it.

Why does this happen?

Packages change Functions are renamed, defaults change and bugs are fixed

Your code depends on them The same code with a different package version can give a different result

Other computers differ A colleague, a new laptop or an HPC: “it works on my machine”

Nothing records it Your project doesn’t say which versions it needs, so nobody can tell what went wrong

What is an environment?

Without environments

One shared library of packages for every project on your computer

With environments

Each project has its own set of packages, at the versions it needs

Project 1 → package v1.2

Project 2 → package v1.3

An environment is a project’s own folder of installed packages. Projects can no longer interfere with each other, and each one has what it needs.

How do environments work?

Lock file → Create the environment → Packages installed

  • The lock file is the recipe: an exact list of packages and versions. It is small, and you keep it with your project
  • The environment is what gets built from it: the installed packages, in their own folder
  • Your code only sees the packages in its own environment
  • The environment is disposable: delete it, and rebuild it from the lock file whenever you like

The tools

Python R
Tool uv renv
Lock file (keep it) uv.lock renv.lock
Environment (disposable) .venv renv/library
Rebuild it uv sync renv::restore()

Other tools do the same job: conda and pixi (which can install Python, R and other software in one environment), and Python’s built-in venv. The idea is the same whichever you use: a file that records what the project needs. Point out that the notes (section 3.2) have a fuller table with conda and pixi in it.

Send your project to someone, and it works

Your project +
lock file → Colleague rebuilds
the environment → Same packages,
same results

✔ Send: your code, README and lock file (and the data, if you can)

✘ Don’t send: the environment itself. It is large, and specific to your computer

This is the payoff. The lock file travels with the project, by email, zip or git. Your colleague, a reviewer, or you on a new laptop runs one command and gets the same packages. You can send it to a reviewer and it will run first time.

What environments don’t cover

  • They record packages. Also write down the version of R or Python in your README (uv can pin Python; renv records the R version but doesn’t install it)
  • The operating system and hardware can still differ
  • They don’t include your data

Good enough for almost every project. Perfect is not the goal!

No code? Record it anyway

Write a list of programs

Record the versions

List your plugins

Note your operating system

All of this can live in your README: the next person then knows what you used!

Sharing your data: Q-FAIR

Q-FAIR data principles

Quality Accurate, complete, documented

Findable Clear names and description

Accessible Clear how to get it

Interoperable Open, standard formats

Reusable Documented, with a licence

Read more: the FAIR principles

Link Q, F and A back to earlier sections (read-only raw data, README, setup notes). The next slides cover I and R. Keep this section brisk: it is a signpost, not a tutorial.

Why it matters

  • Funders and journals increasingly expect data to be shared
  • Others can build on your work, and check it
  • Future you can find and understand your own data
  • Your work gets cited

Quality comes first: there is no point sharing data that nobody can trust or understand.

Four things to do

What to do Learn more
Open formats Share data as CSV, not a format that needs one program Turing Way: research data management
Describe it Write a data dictionary: what each column means, its units and missing values See section 2
Add a licence Data: CC BY 4.0. Code: MIT Creative Commons chooser, choosealicense.com
Deposit it A repository that gives a DOI, such as Zenodo or your institution’s Zenodo

Can’t share the data? Share the README and data dictionary, and explain how to ask for access

Open formats: in Excel use File > Save As > CSV UTF-8, one sheet per file, and note that formulas become values. A data dictionary has one row per column, as in section 2. Check funder and institution requirements for licences. Refer ethics and consent questions to the research data team.
