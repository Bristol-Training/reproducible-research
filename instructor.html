At a glance

How it runs: slides, then (in sections 2 and 3) a short watch-only demo (the “wow”), then one activity: Together (we do a part), Your turn (they do it on their own), Answer (you show it). In the live session, attendees never need to install software or run code: they inspect files in the example folder and explore examples in their browser. The R and Python examples are for them to read, and the optional capstone is where they write their own afterwards. The steps for each demo and activity are in the speaker notes of its slide (press S in the deck).

# Section Min Objective Demo (you) Activity
1 Project structures 25 1 none Rescue the messy project
2 Documentation & Quarto 45 2, 3, 5 Change "Gentoo" to "Chinstrap", update HTML/PDF/Word Be the new colleague. Explore Quarto in the wild
3 Virtual environments 30 4, 5 2023 script crashes today → uv sync rescues it Spot the handover trap & peek inside a lock file
4 Your first step 15 6 none Your checklist
(+) Optional: Q-FAIR +5 6 none Q-FAIR detective

By the end, attendees can:

  1. Organise a project into raw data, processed data, code and outputs, and explain why raw data is never edited.
  2. Describe what a good README and data dictionary contain, and why they matter, particularly for Data Management Plans.
  3. Explain why Quarto helps reproducibility, identify the parts of a Quarto source file, and see how one file makes HTML, PDF and Word.
  4. Explain why package updates break old code, what a lock file records, and what to share (and never share) with a colleague.
  5. Apply these practices to your own coding projects, using the R and Python examples as a starting point.
  6. Choose one practice to start using on your own project, and know where to find out more.

Before you start

  • Download and unzip the example folder. Copy tidy-project/ and environment-demo/python-example/ somewhere you can run them.
  • Section 2 demo: You need R (knitr, rmarkdown) and Quarto 1.4+ on your own machine. Render tidy-project/report.qmd once beforehand to check HTML, Typst PDF and Word all build cleanly.
  • Section 2 activity links (ready to paste into the Zoom/Teams chat):
    • La Palma Earthquakes manuscript: https://quarto-ext.github.io/manuscript-template-jupyter/
    • Quarto Gallery: https://quarto.org/docs/gallery/
  • Section 3 demo: Uses uv in a copy of environment-demo/python-example/. Run both commands in its README.md once beforehand so uv caches the packages locally (the live demo then runs in ~1 second!).

Ground rules

  • Nobody runs code in the live session. Never debug live. If a demo fails, say so, show the ready-made files in tidy-project/outputs/ or environment-demo/, and move on.
  • Demos are watch-only. Activities use the example folder or a web browser.
  • The course is online: no pair work. Every Your turn is done on your own, and people share answers by typing in the chat. Read a few out.
  • Wording works for everyone in the university. Spreadsheet users do the same activities.
  • If running late, skip the optional slides first, then shorten a Your turn, not a section.

1. Project structures (25 min)

Demo: none. Activity: Rescue the messy project: look at messy-project/ together, then on their own they sort every file into raw data, cleaned data, code, results or documents, and you show tidy-project/ as the answer.

Checkpoints: by 5 min Together; by 9 Your turn; by 15 Answer; finish at 25.

Key messages

  • Raw data is never edited. Everything after it can be re-made, so protect the raw data and the code.
  • Raw / processed / code / outputs, in a pipeline.
  • Messy projects happen naturally. Nobody is being criticised.
  • Spreadsheets: same rule. Keep the original, work on a copy.

Don’t forget

  • In Together, let people feel the problem before you explain it.
  • At the Answer, ask who disagreed, and why. There is more than one reasonable layout.

If running late: shorten Together. Watch out for: “it is quicker to fix the typo in the raw file”.

2. Documentation & Quarto (45 min)

Demo: One change, three formats: in a copy of tidy-project/, open report.qmd and outputs/report.html. Change chosen_species <- "Gentoo" to "Chinstrap", render (quarto render report.qmd or the Render button), and show that every number, table and figure updated across HTML, PDF and Word. Activities: Be the new colleague (from messy-project/notes.txt, write down three things they can’t work out; the answer is the README and data dictionary) and Explore Quarto in the wild (browse the La Palma manuscript or the Quarto Gallery, click </> Source on one example, spot two .qmd ingredients, and post in the chat where Quarto would save them copy-pasting).

Checkpoints: by 3 min Be the new colleague (Together); by 13 Quarto slides; by 22 demo; by 26 Explore Quarto, Together; by 28 Your turn; by 34 Answer; finish at 45.

Key messages

  • Four kinds of documentation. Write for the person who will read it.
  • A README answers: what is it, how do I run it, what do I need. A README that is wrong is worse than none.
  • A data dictionary: copying the column names is easy. The descriptions are the value.
  • Quarto: the report is the analysis. No copy and paste. Data changes, so render again.
  • One plain-text .qmd file can make HTML, PDF (via Typst, no LaTeX needed), Word, slides, websites and full journal manuscripts.

Don’t forget

  • Read the messy notes.txt out loud with a straight face.
  • Open the Quarto part with “who has copied a number into Word and then found the data had changed?”
  • At the demo: point out @tbl-sex / @fig-mass turning into Table 1 / Figure 1, change "Gentoo" to "Chinstrap", and open HTML, PDF and Word side by side.
  • Paste the La Palma manuscript and Quarto Gallery links into the chat before Your turn, and point out the </> Source button so everyone knows what to click.

If running late: skip the “old way vs the Quarto way” slide. Watch out for: people thinking they need to write R/Python to use Quarto — remind them Quarto works with plain Markdown too, and they can inspect tidy-project/report.qmd locally at their own pace.

3. Virtual environments (30 min)

Demo: 2023 code meets a 2026 laptop: in a copy of environment-demo/python-example/, run uv run --no-project --with pandas --with matplotlib code/analysis.py — it crashes because NumPy 2.0 removed np.NaN. Then run uv sync and uv run code/analysis.py — uv.lock restores numpy 1.26.4 in ~1 second and the untouched 2023 script runs cleanly. Activity: Spot the handover trap & peek inside a lock file: open environment-demo/python-example/ (pyproject.toml + uv.lock) or environment-demo/r-example/ (code/analysis.R + renv.lock) in any text editor, count the hidden sub-packages recorded inside the lock file, check the exact version of numpy or ggplot2, and decide what goes wrong with Alex’s vague README and Blair’s 450 MB .venv zip.

Checkpoints: by 10 min the demo; by 14 Together; by 16 Your turn; by 22 Answer; finish at 30.

Key messages

  • “It worked last year”: packages change, and installing 1 or 2 packages silently pulls in a dozen sub-packages underneath.
  • An environment is a project’s own packages. The lock file is the plain-text recipe, and the environment folder is disposable.
  • Send your project to someone: the code, README and lock file — never the .venv or renv/library folder. They rebuild it with one command.
  • What it doesn’t cover: the R or Python version (write it in the README; uv can also pin Python), the operating system, the data.
  • Spreadsheets: write the program, version and add-ins in the README.

Don’t forget

  • Spend the time on the why. In the demo, highlight that the author only asked for pandas and matplotlib — numpy updated behind the scenes!
  • Remind attendees that uv.lock and renv.lock are ordinary text files they can open in Notepad, TextEdit or any editor.
  • Seeing 14 packages in uv.lock (from 2!) or 18 packages in renv.lock (from 1!) is the lightbulb moment.

If running late: drop the “tools” slide. Watch out for: the demo going wrong (uv not found). If it does, open environment-demo/python-example/uv.lock directly, point to numpy 1.26.4, and move straight into the activity.

4. Your first step (15 min)

Demo: none. Activity: Your checklist: they tick the checklist for a project of their own (or the messy one), circle one thing to start with, and post it in the chat. Optional extra: Q-FAIR detective.

Checkpoints: by 3 min the checklist; by 9 Quick wins; by 12 the recap; finish at 15.

Key messages

  • The whole course is one journey: messy, tidy, documented, reported, recorded, shareable.
  • Each habit is small. Pick one and do it this week.
  • Start with a quick win: a README takes 15 minutes.

Don’t forget

  • Ask people to circle one thing, and post it in the chat.
  • Point out the printable checklist in the example folder (checklist.pdf and checklist.docx).
  • Go back to the six objectives and tick them off.
  • Mention the separate git and GitHub course.
  • Point people to the capstone exercise (Putting it all together, linked from the home page), to try after the course: a tidy project, an environment (R or Python) and a report with code, from scratch.

If time: the optional slides after Thank you cover Q-FAIR (the principles, why it matters, four things to do) and a Q-FAIR detective activity. Watch out for: nothing, except people leaving with a long to-do list. One thing is enough.
